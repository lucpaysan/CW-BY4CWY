# CW 解码优化方案：实验记录与结论

> 目的：降低 DeepCW 在「字符间隔过小」场景下的误识率
> 日期：2026-10-04

---

## 一、问题定义

实测发现的失效场景（`charGap=1.2`，远小于标准的 3）：

| 模型输出 | 参考文本 | CER |
|---|---|---|
| `CQ B BASJW` | `CQ DE BY4CWY` | 60% |
| `UR T5S39 QD` | `UR RST 579 QSL` | 55% |
| `B3ASJW B BJC` | `BY4CWY DE BG1ABC` | 79% |

必须区分两类失败：

| 类型 | 特征 | 后处理能解决吗 |
|---|---|---|
| **真粘连** | 字母全对，只是没切分开（`CQDEBY4CWY`） | 能 |
| **误识** | 字母本身就错了（`DEBY4CWY` → `BASJW`） | **不能** |

实测样本以**误识**为主，所以「连读重切分」这类后处理无法改善 CER。

---

## 二、已否决的方案（重要，勿再尝试）

### 方案 1：偏移窗口投票 ❌

同一段音频切多个偏移窗口，各自推理后按绝对时间戳对齐投票。

```
单窗口CER 24.7%  →  3窗 31.0%  →  5窗 30.0%
```

**为什么失败**：
- 偏移裁剪必然丢失信号（`CQ DE BY4CWY` 偏移 0.35s 后首字母 C 被切掉）
- `reflect` 填充的内容随窗口起点变化，边缘帧的输入分布变了
- 表现为首字符频繁丢失：`CQ`→`Q`、`BY4CWY`→`Y4CWY`

### 方案 2：多相位 hop 投票 ❌

同一段音频用不同 hop（48/72/96）各算一次频谱。

```
单窗(48) CER 24.7%  →  双相(48,72) 57.8%  →  三相(48,72,96) 63.8%
```

**为什么失败（关键洞察）**：

> DeepCW 只在 `hop=48` 下训练过。`hop=72/96` 是**分布外输入**，
> 模型输出接近乱码。投票把乱码混进结果，反而严重污染。

**hop=48 与频带 400-1200Hz 是模型的硬约束，不是可调超参。**
任何改变输入分布的「投票」都会失效。

## 三、可行的方向：跨模型集成

### 实测互补性

同一批样本，两个模型的表现：

| 用例 | DeepCW CER | CWformer CER | 逐位互补度 |
|---|---|---|---|
| 粘连-CQ DE BY4CWY | 60% | 50% | **88%** |
| 粘连-UR RST 579 QSL | 55% | 64% | **89%** |
| 粘连-BY4CWY DE BG1ABC | 79% | 57% | **100%** |
| 粘连-CQ CQ DE BY4CWY K | 54% | 38% | **92%** |
| 中等抖动-CQ DE BY4CWY | 0% | 10% | 10% |
| 标准-CQ DE BY4CWY | 0% | 10% | 10% |
| 标准-BY4CWY DE BG1ABC | 0% | 7% | 7% |
| 标准-QTH SHANGHAI | 0% | 9% | 9% |
| 标准-CQ CQ DE BY4CWY K | 0% | 8% | 8% |
| 强抖动-BY4CWY DE BG1ABC | 0% | 14% | **100%** |
| **平均** | **24.7%** | **26.7%** | — |

### 关键结论

1. **整体 CER 两者接近**（24.7% vs 26.7%），单看平均没有优势
2. **但在粘连场景互补度高达 88-100%** —— 逐位几乎完全不同
3. 标准场景两者都对（互补度低是因为都答对了）

**这正是集成的理想条件**：各有优势 + 失败模式不同 → 仲裁有选择空间。

对比：同模型变体（偏移/多 hop）互补度是 0（本来就该 0），
跨模型才有真互补。

## 四、已实现的仲裁策略

`src/engines/engineRegistry.ts`

```typescript
export function arbitrate(results: EngineResult[]): {
  text: string;
  source: EngineId | "consensus" | "none";
  agreement: number;   // 公共前缀占比，作为一致度指标
}
```

**决策顺序**：

1. 全部为空 → `none`
2. 只有一个有输出 → 直接采用
3. 两者一致（忽略空格）→ `consensus`，置信度最高
4. 不一致 → **按结构化信号数量仲裁**：
   `呼号×3 + 报告×2 + Q码×1`，能提取出更多通联要素的更可信
5. 结构化信息相同 → 取模型置信度更高者

**为什么用「结构化信号」而不是「多数票」**：
两个引擎输出长度可能不同、错位，逐位投票不可靠。
而「能否提取出合法呼号/信号报告」是独立于对齐的强信号——
能从乱码里稳定提取出 `BY4CWY` 的那个模型更可信。

### 引擎健康与自动降级

```typescript
class EngineRegistry {
  markLoaded(id)      // 标记就绪
  markFailed(id)      // 连续失败 3 次则禁用
  markSuccess(id)     // 成功则重置计数
  available(prefs)    // 返回可用引擎（排除禁用）
}
```

作用：CWformer 是 79MB 大模型，加载失败或内存不足时自动降级到 DeepCW，
保证社团现场演示不会因为大模型加载失败而卡死。

## 五、两个引擎的对比

| 维度 | DeepCW | CWformer |
|---|---|---|
| 许可 | **AGPL-3.0** | **MIT** |
| 架构 | CRNN + CTC | 全因果 Conformer + CTC |
| 采样率 | 3200 Hz | 16000 Hz |
| 参数量 | — | 19.5M |
| 模型体积 | 14 MB | INT8 24MB / FP32 79MB |
| 流式 | 否 | 是（KV cache） |
| 词表 | 42 类，**无缩写** | 52 类，**含 AR/SK/BT/KN/AS/CT** |
| 标准场景 CER | **0%** | 7-14% |
| 粘连场景 CER | 55-79% | **38-64%** |
| 前端复杂度 | 低（无 KV cache） | **高**（51 个状态张量需维护） |

**选型建议**：
- 追求简单稳定、只用 DeepCW（注意 AGPL）
- 追求极限鲁棒、且能接受移植成本 → 加 CWformer 做仲裁

## 六、遗留工作

1. **CWformer 尚未接入浏览器**
   需移植：40-bin log-mel 前端（含 `mel_basis.npy` 查表）、
   16kHz 重采样、51 个 KV/conv 状态张量的滑动窗口管理

2. **已知缺陷：粘连串内嵌呼号时重切分保护失效**
   `BY4CWYDEBG1ABC` → `BY 4C WY DE BG 1AB C`
   原因：`isAtomic` 只检查整段，不检查 DP 内部候选子串。
   需给 DP 加子串级呼号保护。

3. **CWformer 的浏览器端 INT8 兼容性未验证**
   `onnxruntime-web` 对 INT8 算子支持有限，可能被迫用 FP32（79MB）

4. **仲裁策略尚未用真实双模型输出验证**
   当前的仲裁测试用的是构造数据，应该在 CWformer 接入后
   用真实输出重跑，验证仲裁能否真的降低端到端 CER。
